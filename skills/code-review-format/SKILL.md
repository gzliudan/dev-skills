# 代码评审输出规范

规则只在此定义一次；`assets/review-template.md` 只提供骨架

## 步骤

1. 定范围：先 `git status`，再取 base（命令见下）；定不了先问再做
2. 读上下文：模块职责、对外接口、调用方
3. 构建与测试：逐 commit 跑，失败即 A（规则见「构建与测试」）
4. 通读 diff：按「维度」过，形成候选条目
5. 验证证据：读到确切行；无证据即丢弃，不凭记忆或 diff 行号推测
6. 定位引入提交：按「引入提交」给每条候选定 commit；构建/测试失败填首个失败 commit；定不了如实写，不猜
7. 分级编号：按「分级」「编号」分配
8. 核对：复核 `file:line`、引入提交 hash 与源码/历史一致；构建与测试结果与命令输出一致；复审另须回填上轮状态、确认代码变更
9. 自检：证据、构建与测试、复审回填按前述规则自查；格式按「条目」「结构」「风格」逐项过
10. 输出：套模板，删注释与占位符；措辞按「风格」

## 范围

- base = 上游追踪分支的 merge-base；用户指定 commit range 时以其为准；都定不了先问再做

  ```bash
  base=$(git merge-base origin/HEAD HEAD)   # 或 upstream/<branch>
  git diff --stat "$base...HEAD"            # 变更文件
  git log --date=format-local:'%Y-%m-%d %H:%M:%S' --pretty=format:'%cd %h %s' "$base..HEAD"   # 提交历史，直接用于范围行
  git diff "$base...HEAD"                   # 完整 diff
  ```

  PowerShell：`$base = git merge-base origin/HEAD HEAD`，其余同上（格式串沿用单引号字面量，避免 `$` 被展开）；单 commit：`git show -s --date=format-local:'%Y-%m-%d %H:%M:%S' --pretty=format:'%cd %h %s' <hash>`

  本环境（CodeBuddy）用 `execute_command` 跑上述 git 命令；读源码用 `read_file`，定位符号用 `search_content` / `search_file` / `list_dir`

- 变更过大（diff > 1500 行或文件 > 30）按模块分批读，仍须全覆盖；覆盖不到的在「待确认」声明
- 排除生成文件、依赖目录、锁文件、纯格式改动
- 标题固定「代码评审报告」，标题下用 `-` 列表给出四项：
  - 版本号：`- 版本号： v1`（初审 v1，每轮复审 +1，不回退不复用）
  - 评审时间：生成时刻，`YYYY-MM-DD HH:MM`
  - 评审范围：用缩进两空格的二级列表逐行列出：每行 `<提交时间> <hash> <title>`，时间取 committer date、格式 `YYYY-MM-DD HH:MM:SS`；hash 长度统一；多 commit 父在前；分支范围写 `<分支 → base>`
  - 构建与测试：`- 构建与测试：<命令>；<通过数>/<总数> commit 通过`；失败时用缩进二级列表追加 `- <hash>：<编译 / 测试>失败，<首个失败用例或错误摘要>`；未跑的 commit 写 `- <hash>：未执行（<原因>）`
- 边界：空 diff → 回复「无变更可评审」不出报告；未提交改动默认不评，用户要求时范围行写 `<时间> <工作区>（未提交改动，基于 <hash>）`；命令取不到或跑不起来 → 构建与测试行写 `- 构建与测试：未执行（<原因>）`，并在「待确认」声明未验证

## 构建与测试

- 命令：先取 CI 配置、Makefile / package.json scripts / README 构建说明；取不到再按语言惯例（`go build ./... && go test ./...`、`npm run build && npm test`、`cargo test`、`pytest` 等）；不臆造命令
- 逐 commit：按评审范围从父到子依次检出 `git checkout --detach <hash>` 执行；工作区有未提交改动时改用 `git worktree add <dir> <hash>`，不污染当前工作区，结束 `git worktree remove <dir>`
- 顺序：先跑最新 commit；失败时用 `git bisect run <命令>` 或二分定位首个失败 commit，其前的 commit 视为通过；最新通过且 commit 多 / 单次构建慢时按二分抽查，未实际执行的 commit 逐一在构建与测试行写明「未执行（<原因>）」
- 判定：
  - 编译失败、测试失败、测试 panic / 超时 → 一律 A 致命问题，不降为 B 及以下
  - 同一失败根因只在首个失败 commit 记一条（不拆多条）；后续 commit 沿用该编号，仍失败标「未修复」，已修好标「已修复（证据：<命令> 通过）」
  - base 上已失败（存量）→ 加 `（存量）`，不阻塞；范围内新引入的失败照常归 A
  - 环境 / 依赖 / 工具链缺失导致跑不起来 → 不列为问题，列入「待确认」，写明未验证
- 条目：按「条目」六字段书写；代码位置填编译错误 / 失败用例指向的 `file:line`，无文件指向时填 `构建输出（无文件定位）`；描述引用命令输出摘要，受「风格」≤ 十余行限制
- 引入提交：填首个失败 commit；二分仍无法唯一定位时填 `未能唯一定位（候选：<hash>）`
- 复审：重跑本轮范围的构建与测试，结果与上轮逐条比对，不沿用上轮结论

## 维度

逐项过一遍，不要求每项有产出

- 正确性：空值/零值/越界/溢出、边界、编码序列化、状态机
- 错误处理：吞错、包装丢上下文、panic、重试幂等、超时取消
- 并发时序：竞态、锁粒度与死锁、共享可变状态、初始化顺序
- 安全：注入、越权与鉴权绕过、敏感信息落盘/日志、输入校验
- 资源：泄漏、句柄未关闭、无上限缓存与队列
- 性能：N+1、复杂度退化、热路径分配、批量化缺失
- 兼容与数据：接口/协议兼容、迁移回滚、默认值变更
- 可测性：缺关键测试、断言不足、依赖不可注入
- 可维护性：命名、重复代码、抽象层次、注释与实现一致

## 分级

- A 致命问题：不可逆损失或安全边界被突破。例：资产损失、共识分叉、签名/权限绕过、数据永久损坏、构建或测试失败
- B 严重问题：功能错误或运行时故障，可回滚修复。例：逻辑错误、panic/死锁、状态不一致、性能数量级退化、协议不符
- C 一般问题：正确性无立即影响，特定条件下恶化。例：边界未处理、错误被吞、资源未释放、低概率竞态
- D 轻微问题：不影响运行时行为。例：命名、注释、冗余代码、格式
- E 改进意见：非缺陷的改进机会。例：架构简化、抽象调整、可选优化、可读性

无法归级取较低级并说明理由；构建 / 测试失败不适用降级，一律归 A（见「构建与测试」）

## 编号

- 编号 = 类别词 + 级别前缀 + 序号：A~D 用「问题」（`问题A1`、`问题B1`），E 用「意见」（`意见E1`）；终身唯一：不复用、不重排、跨轮接续最大序号
- 全文不出现裸编号（条目标题、`撤回（合并至 …）`、`撤回（级别调整，见 …）`、复审精简条目）
- 级别变更：旧编号标 `撤回（级别调整，见 问题B3）`，新级别下以 `新问题` 开 `问题B3`
- 同根因合并至最早编号，其余标 `撤回（合并至 问题X1）`（X 为级别前缀）

## 结论与计数

结论由新问题、未修复的条目决定：

- A ≥ 1 或 B ≥ 1 或 C ≥ 1 → 否决
- A = B = C = 0（仅 D / E）→ 通过

结论后面附条目数量，只列非零组别，例如：

- `否决（严重问题×1，一般问题×2）`
- `通过（轻微问题×2，改进意见×1）`

全部条目均为已修复 / 撤回（无新问题、未修复）→ 结论写 `通过`，不附计数

## 条目

对问题进行分组，按以下次序输出：致命问题、严重问题、一般问题、轻微问题、改进意见

每个组内按编号列全部条目；空组跳过，不输出该组标题及任何占位。每条 = 标题行 + 六个字段，均以列表项书写：

- 标题：`#### 问题A1：<标题>`（E 级 `#### 意见E1：<标题>`）
- 描述：问题 + 触发条件 + 后果，内联 `file:line`，证据须实读
- 代码位置：`file.go:120-135`（`funcName`）；diff 未改动的历史代码加 `（存量）`（只提示不阻塞）；多处用缩进二级列表
- 引入提交：`<hash>`；规则见「引入提交」
- 修复建议：行为改动附 diff 片段（独立代码块）；删除/改名/调序一句话
- 验证方法：复现步骤 / 回归测试 / 断言点三选一；E 级填 `不适用`
- 状态：见下

四种状态：

- 新问题：本轮新发现，完整字段（含引入提交）
- 已修复：上轮已修好，终态：标题行 + `- 状态：已修复（证据：…）`
- 未修复：复审仍成立，非终态：下轮回填完整字段（含引入提交）
- 撤回：误报/不成立/合并/级别调整，终态：标题行 + `- 状态：撤回（理由：…）`，编号不复用

已修复 / 撤回 为精简条目，只保留标题行 + 状态行，不写其余字段，引入提交随之省略。

### 引入提交

- 内容：引入该问题的 commit，只写 `<hash>`，不写 commit 标题；hash 长度与「评审范围」一致：`git log --abbrev=<n>` 与 `git blame --abbrev=<n>` 用同一 `<n>`，范围行的 `%h` 随之同长
- 定位：`git blame -L <start>,<end> -s -- <file>` 取引入行的 commit；行被多次改动时取引入问题语义的那一版
- blame 不可靠（移动、重命名、格式化、批量替换）时用 `git log -L <start>,<end>:<file>` 或 `git log -S "<关键片段>" --oneline -- <file>` 交叉确认
- 多处引入：按代码位置顺序用缩进二级列表逐条列出；同一 commit 引入多处只列一次
- 存量判定：`git merge-base --is-ancestor <hash> "$base"` 成立即不在评审范围 → 加 `（存量）`，与「代码位置」的存量标注一致，不阻塞
- 未提交改动引入：填 `工作区（未提交，基于 <base hash>）`
- 无法唯一定位（合并、重构、生成代码）→ 填 `未能唯一定位（候选：<hash>）`，不猜测
- PowerShell 命令同上，格式串沿用单引号字面量

## 待确认

- 无则跳过
- 读得到代码且能判定不成立 → 丢弃
- 缺调用方、配置、上下游等外部信息 → 列入待确认（不列为条目、不参与编号）
- 每条一个列表项：`- <事项>：缺 <信息>；需确认 <问题>；若最坏情况成立则归 <级别>`
- 复审收口写在其下缩进一行 `- → 已澄清：见 问题C3` 或 `- → 仍待确认：<进展>`

## 复审

- 前置：必须拿到上一轮报告；拿不到先索取，不得编造历史编号
- 沿用初审范围（变化须声明并重述）；评审时间取本轮时刻；版本号 +1
- 上轮全部条目须回填状态：已修复 / 撤回用精简条目，其余给完整字段（含引入提交；引入提交不变则沿用，代码被改动则重新定位）
- 范围因 rebase / amend 变化时，引入提交须重新定位，不沿用旧 hash
- 上轮待确认项逐条收口

## 结构

评审范围 → 总体结论 → 问题清单 → 待确认

- 默认输出到对话；用户指定路径以其为准

## 风格

- 结论先行，不铺垫、不复述 diff
- 不贴大段源码（修复建议片段除外，≤ 十余行），其余用 `file:line` 指路
- 每条自包含，不写「同上」，需关联时用编号引用
- 语气确定，禁止「可能有问题」「建议确认一下」，不写定性评价，不评价作者

## 禁止

1. 无 `file:line` 证据，或把未读过的代码写成结论
2. 范围外代码，除非标 `（存量）` 且不阻塞
3. 同一根因拆成多条
4. 把设计偏好包装成缺陷
5. 引入提交未经 blame / log 核实，或猜测一个 hash 填上
6. 未实际执行构建 / 测试却写「通过」，或把跑不起来说成通过
